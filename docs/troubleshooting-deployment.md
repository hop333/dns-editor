# Проблемы при развёртывании и их устранение

Во время развёртывания DNS Editor на VPS были выявлены типовые ошибки, связанные с переносом проекта с Windows на Linux, настройкой BIND, делегированием домена и проверкой DNS-записей. Ниже приведён краткий разбор проблем, их причин и способов устранения.

## 1. Ошибки запуска shell-скриптов

**Сообщения об ошибке:**

```text
scripts/deploy.sh: line 16: $'\r': command not found
set: pipefail: invalid option
```

**Причина:** shell-скрипты были подготовлены в Windows и содержали переводы строк CRLF (`\r\n`), которые некорректно обрабатываются в Linux.

**Решение:**

```bash
find scripts -name '*.sh' -exec sed -i 's/\r$//' {} +
sed -i 's/\r$//' .env
```

Позже упаковочный скрипт `scripts/package-for-server.ps1` был доработан так, чтобы shell-файлы попадали в архив с LF-переводами строк.

## 2. Ошибки чтения `.env`

**Сообщение об ошибке:**

```text
.env: line 3: $'\r': command not found
```

**Причина:** файл `.env` также содержал Windows-переводы строк CRLF.

**Решение:** преобразовать `.env` в Linux-формат:

```bash
sed -i 's/\r$//' .env
```

или пересоздать `.env` непосредственно на сервере.

## 3. Генерация `rndc.key`

**Сообщение об ошибке:**

```text
rndc-confgen: create keyfile: invalid file
```

**Причина:** вариант генерации ключа через `-c /dev/stdout` не подошёл для используемого Docker-образа `ubuntu/bind9`.

**Решение:** генерировать ключ сразу в смонтированную директорию `config`:

```bash
docker run --rm -v "$PWD/config:/etc/bind" ubuntu/bind9:latest \
  rndc-confgen -a -A hmac-sha256 -c /etc/bind/rndc.key
chmod 644 config/rndc.key
```

## 4. Контейнер BIND не стартует

**Сообщения в логах:**

```text
open: /etc/bind/rndc.key: permission denied
loading configuration: permission denied
dependency failed to start: container dns-server is unhealthy
```

**Причина:** процесс `named` внутри контейнера запускается от пользователя `bind`, который не мог прочитать файл `rndc.key`.

**Решение:**

```bash
chmod 644 config/rndc.key
docker compose up -d
```

После исправления прав контейнер `dns-server` переходил в состояние `healthy`.

## 5. Порт 53 занят `systemd-resolved`

**Вывод диагностики:**

```text
127.0.0.53:53  systemd-resolved
```

**Причина:** локальный stub DNS-сервис `systemd-resolved` слушал адрес `127.0.0.53:53`. Для Docker-развёртывания это обычно не мешает, если BIND публикуется на `0.0.0.0:53`.

**Решение:** при необходимости отключить stub listener:

```bash
sudo nano /etc/systemd/resolved.conf
```

и установить:

```ini
DNSStubListener=no
```

затем перезапустить сервис:

```bash
sudo systemctl restart systemd-resolved
```

## 6. REG.RU не видит IP у `ns1`

**Сообщение регистратора:**

```text
Невозможно получить IP-адрес ns1.jsthope.online
```

**Причина:** при переходе на собственные NS возникает ситуация “курица и яйцо”: чтобы домен начал использовать `ns1.jsthope.online`, регистратор должен знать IP-адрес этого NS. Для этого нужны glue-записи.

**Решение:** на стороне текущего DNS-провайдера или в панели REG.RU/ISPmanager добавить A-записи:

```text
ns1.jsthope.online -> 161.104.32.224
ns2.jsthope.online -> 161.104.32.224
```

После этого в карточке домена можно указать собственные NS:

```text
ns1.jsthope.online
ns2.jsthope.online
```

## 7. `ns2` возвращает NXDOMAIN

**Сообщение:**

```text
не удалось найти ns2.jsthope.online: Non-existent domain
```

**Причина:** была создана A-запись только для `ns1`, но отсутствовала запись для `ns2`.

**Решение:** добавить A-запись:

```text
ns2.jsthope.online -> 161.104.32.224
```

## 8. `nslookup` на IP сервера завершается тайм-аутом

**Сообщение:**

```text
DNS request timed out
nslookup jsthope.online 161.104.32.224
```

**Причина:** с домашнего ПК UDP-запросы на порт 53 могут блокироваться провайдером, локальной сетью или особенностями Windows. При этом BIND на сервере может работать корректно.

**Решение:** использовать несколько способов проверки:

```bash
dig @127.0.0.1 jsthope.online A
dig @161.104.32.224 jsthope.online A
nslookup jsthope.online
```

Также необходимо открыть порт DNS:

```bash
sudo ufw allow 53/udp
sudo ufw allow 53/tcp
```

Для дополнительной диагностики использовался `tcpdump`, который показывал, доходят ли внешние DNS-запросы до VPS.

## 9. `ufw` не установлен

**Сообщение:**

```text
sudo: ufw: command not found
```

**Причина:** firewall `ufw` не был установлен в системе.

**Решение:**

```bash
sudo apt update
sudo apt install ufw
```

После установки были открыты необходимые порты: `22`, `53`, `80`, `3000`, `8000`. В дальнейшем для production-развёртывания порты `3000` и `8000` рекомендуется закрыть за reverse proxy.

## 10. Домен указывает на старый IP

**Симптом:**

```text
jsthope.online -> 31.31.197.28
NS -> ns1.hosting.reg.ru
```

**Причина:** домен всё ещё был делегирован на DNS-хостинг REG.RU, а не на собственный BIND-сервер.

**Решение:** в карточке домена заменить NS на:

```text
ns1.jsthope.online
ns2.jsthope.online
```

После обновления делегирования домен начал разрешаться в IP VPS `161.104.32.224`.

## 11. Веб-редактор не загружается

**Симптом:** страница на `:3000` открывается, но интерфейс не догружается или отображается бесконечная загрузка.

**Причина:** фронтенд был собран с неправильным значением `NEXT_PUBLIC_API_URL`, поэтому браузер обращался не к тому API.

**Решение:**

```env
NEXT_PUBLIC_API_URL=http://161.104.32.224:8000
```

Затем пересобрать фронтенд:

```bash
docker compose build --no-cache frontend
docker compose up -d
```

Веб-интерфейс нужно открывать на порту `3000`, а порт `8000` использовать только как API.

## 12. Ошибка `dig` в PowerShell

**Сообщение:**

```text
Отсутствует имя свойства после @
```

**Причина:** в PowerShell символ `@` имеет специальное значение, поэтому команда `dig @161.104.32.224 ...` может интерпретироваться некорректно.

**Решение:** использовать кавычки:

```powershell
dig "@161.104.32.224" jsthope.online A
```

или использовать `nslookup`.

## 13. На `http://jsthope.online` отображается страница Яндекса

**Причина:** на порту `80` не был настроен собственный веб-сервер для домена.

**Решение:** установить и настроить nginx, затем разместить простой `index.html` для проверки работы HTTP-сайта.

## 14. Кракозябры на HTML-заглушке

**Причина:** HTML-страница была создана без явного указания кодировки UTF-8 или записана в неподходящей кодировке.

**Решение:** добавить в `<head>`:

```html
<meta charset="utf-8">
```

и убедиться, что файл сохранён в UTF-8.

## 15. Тестовые DNS-записи не видны

**Симптомы:**

```text
Non-existent domain
dig @127.0.0.1 test-a.jsthope.online A
```

**Причина:** запись была добавлена в интерфейсе, но зона не была сохранена в файл. В редакторе добавление строки и сохранение зоны являются разными действиями.

**Решение:**

1. Добавить запись в интерфейсе.
2. Нажать “Сохранить зону”.
3. Нажать “Перезагрузить BIND”.
4. Проверить наличие записи в zone-файле:

```bash
grep test-a zones/db.jsthope.online
```

5. Проверить DNS-ответ:

```bash
dig @127.0.0.1 test-a.jsthope.online A
```

## Вывод

Основные проблемы при развёртывании были связаны не с логикой приложения, а с окружением: различиями Windows/Linux, правами на конфигурационные файлы BIND, особенностями делегирования NS у регистратора и сетевой диагностикой DNS. После устранения этих проблем была подтверждена полная цепочка работы: изменение DNS-записи в веб-интерфейсе, сохранение zone-файла, перезагрузка BIND и получение корректного DNS-ответа из внешней сети.
